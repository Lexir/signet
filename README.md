# Signet

Сервис полуавтоматических ответов на почту с валидацией менеджером.

Поток: читает входящие письма по IMAP → генерирует черновик ответа через LLM
(OpenAI или локальная Ollama; на языке клиента + перевод на русский) →
отправляет менеджеру в Telegram на
валидацию (одобрить / отредактировать / отклонить) → после одобрения отправляет
ответ клиенту по SMTP того же ящика поддержки. Человек всегда в контуре: без
подтверждения менеджера клиенту ничего не уходит.

## Стек

- Java 25, Spring Boot 4.1, Spring Framework 7
- Spring AI 2.0 (ChatClient: OpenAI или локальная Ollama, выбор в UI)
- Spring Modulith 2.0 (границы модулей + Event Publication Registry как транзакционный outbox)
- PostgreSQL 16 + Flyway
- Jakarta Mail (IMAP) + Spring Mail (SMTP)
- telegrambots 8 (long polling)
- UI — отдельный SPA на Vite + React + TypeScript (Chart.js), отдаётся как статика из jar
- Spring Security (вход формой + сессия, CSRF через cookie), Actuator
- Сборка — Gradle (Kotlin DSL); фронтенд — npm (`frontend/`)

## Модули

| Модуль      | Ответственность |
|-------------|-----------------|
| `ingest`    | IMAP-опрос, парсинг, дедуп, фильтр авто-ответов → событие `EmailReceived` |
| `context`   | память диалога: треды, реплики в ролях, sliding window + summary |
| `ai`        | генерация черновика и перевода (ChatClient), сервис перевода |
| `review`    | Telegram-бот: отправка на валидацию, approve/edit/reject |
| `send`      | сборка reply, отправка по SMTP, запись в память диалога |
| `recovery`  | досбор зависших писем после рестарта, напоминания о ревью (`@Scheduled`) |
| `analytics` | метрики и веб-дашборд |
| `settings`  | настройки интеграций и ящиков через UI, шифрование секретов |
| `shared`    | доменные сущности, репозитории, события (OPEN-модуль) |
| `config`    | безопасность (basic auth, rate limit, блокировка переборов), async |

Связь между модулями — только доменными событиями (`shared.event.Events`) через
`@ApplicationModuleListener`. Границы проверяет `ModularityTests`.

## Стейт-машина письма

`RECEIVED → DRAFTING → DRAFTED → PENDING_REVIEW → (APPROVED | EDITED | REJECTED) → SENDING → SENT`
(терминальные `REJECTED`, `FAILED`, `IGNORED`).

Письма, классифицированные как неличные (рассылки, сервисные, спам), уходят из
`DRAFTING` в `IGNORED` ещё до вызова модели — ответ по ним не генерируется.

## Быстрый старт (Docker Compose)

Нужен только Docker (Compose v2 входит в комплект). JDK, Gradle и Node на хосте
не требуются: приложение ставится **готовым образом из GHCR** —
[`ghcr.io/lexir/signet`](https://github.com/Lexir/signet/pkgs/container/signet)
(мультиарх: `linux/amd64` для серверов, `linux/arm64` для Apple Silicon).
Сборка из исходников тоже возможна (см. ниже) — Docker соберёт всё сам.

### Установка одним скриптом

[`install.sh`](install.sh) делает всё сам: спрашивает логин/пароль панели и пароль
БД (или генерирует), создаёт `.env` (права 600) с `SETTINGS_SECRET_KEY`, логинится
в GHCR при необходимости и поднимает сервис. Спросит **домен** — и тогда сам
выпустит TLS-сертификат (Let's Encrypt) и переключит nginx на HTTPS; Enter —
останетесь на http.

```bash
mkdir signet && cd signet
curl -fsSL -o install.sh https://raw.githubusercontent.com/Lexir/signet/main/install.sh
bash install.sh
```

Репозиторий и образ публичны — токен и `docker login` не нужны. Повторный запуск
безопасен: существующий `.env` не трогается. Для HTTPS домен должен указывать
A-записью на этот сервер (на голый IP LE не выдаёт).

### Установка вручную

1. Получите файлы проекта (нужны только `docker-compose.yml`, `nginx/` и `.env`):

   ```bash
   git clone https://github.com/Lexir/signet.git && cd signet
   ```

2. Подготовьте `.env`:

   ```bash
   cp .env.example .env
   openssl rand -hex 32          # результат вписать в SETTINGS_SECRET_KEY
   ```

   Обязательны `SETTINGS_SECRET_KEY`, `DASHBOARD_USER`, `DASHBOARD_PASS`, `DB_PASS` —
   без них compose откажется стартовать. Остальное (почта, Telegram, OpenAI)
   можно оставить пустым и заполнить потом на `/settings`.

3. Запуск и проверка (образ в GHCR публичный — логин не нужен):

   ```bash
   docker compose pull app       # скачать образ из GHCR
   docker compose up -d
   docker compose ps             # app должен стать healthy, не просто running
   ```

   Интерфейс — http://localhost:8080/ (вход из `DASHBOARD_*`), health —
   `/actuator/health`.

4. На `/settings` заведите ящик, бота и модель. С этого момента источник
   истины — БД, а переменные из `.env` больше не перечитываются.

### Сборка из исходников (вместо образа из GHCR)

Если правите код или не хотите тянуть образ — Docker с BuildKit соберёт всё сам
(node-стадия для фронта + Gradle для бэкенда):

```bash
docker compose up --build -d
```

Собранный образ получит тот же тег `ghcr.io/lexir/signet:latest` локально;
следующий `docker compose up -d` будет использовать его, пока вы не сделаете
`docker compose pull app`.

### Reverse proxy (nginx) и HTTPS

В compose входит nginx — единственная точка входа снаружи (порты 80/443).
Он проксирует на `app:8080` и передаёт `X-Forwarded-*`, по которым приложение
видит реальные IP клиентов (rate limit, блокировка перебора пароля).

TLS проще всего включить через `install.sh` (спросит домен, сам выпустит
сертификат certbot и переключит nginx на HTTPS с авто-продлением). Это работает
и на **уже поднятом http-инстансе** — запустите `install.sh` повторно, и он
предложит включить HTTPS. Вручную — инструкция в шапке
[`nginx/default.conf`](nginx/default.conf); `COOKIE_SECURE` в `.env` держите
`true` под HTTPS и `false` для отладки по голому http (иначе session-cookie по
http не установится и вход зациклится на форме).

### Что важно знать

- **Приложение и БД слушают только `127.0.0.1`.** Наружу смотрит только nginx;
  прямой порт `8080` оставлен на петле для отладки с самого сервера.
- **Профиль по умолчанию — `prod`** (`SPRING_PROFILES_ACTIVE` в `.env`).
- **`SETTINGS_SECRET_KEY` менять нельзя** после того, как в БД появились секреты:
  старые значения расшифруются в мусор, и все пароли придётся вводить заново.
  Ключ стоит забэкапить отдельно от базы.
- **Пароль БД задаётся только в `.env`** (`DB_PASS`); compose требует его через
  `${DB_PASS:?}` и падает с внятной ошибкой, если он не задан. В самом пароле
  **не используйте символ `$`** — compose трактует его как начало переменной.
- **Пароль postgres применяется только при первой инициализации тома.**
  Поменяли после запуска — нужно `docker compose down -v` (это сотрёт данные).
- **Ollama на хосте** доступна как `host.docker.internal`, не `localhost`.
- **Таблицы живут в схеме `signet`, не в `public`** (`DB_SCHEMA`). Схему создаёт
  Flyway на первом запуске. В psql удобно сразу сделать `SET search_path TO signet;`,
  иначе `\dt` покажет пустоту.

### Обновление и обслуживание

```bash
docker compose pull app && docker compose up -d      # обновиться до свежего образа
docker compose up --build -d          # пересборка из исходников после правок кода
docker compose logs -f app            # логи
docker compose down                   # остановить, данные сохранить
docker compose down -v                # остановить и стереть БД
docker compose exec db psql -U signet -d signet      # консоль БД
```

Кэш Gradle смонтирован через BuildKit, поэтому повторная сборка после правки
кода занимает секунды вместо повторной выкачки зависимостей.

Опубликовать новый образ в GHCR (мультиарх, с Mac через buildx):

```bash
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/lexir/signet:latest --push .
```

## Локальный запуск (без Docker)

Требуется запущенный PostgreSQL. Gradle wrapper уже в репозитории, а JDK 25
скачивается автоматически через toolchain (плагин foojay) — ставить его руками не нужно.

```bash
./gradlew bootRun        # профиль local подхватывается сам
```

UI — отдельный Vite SPA (`frontend/`). Два режима:

```bash
# 1) Разработка фронта с hot-reload: Vite на :5173 проксирует /api на бэкенд :8080
cd frontend && npm ci && npm run dev

# 2) Собрать SPA в статику, чтобы бэкенд отдавал её сам с http://localhost:8080/
cd frontend && npm ci && npm run build   # → frontend/dist, Gradle кладёт её в jar
```

Задача Gradle `copyWebApp` копирует `frontend/dist` в статику jar при `build`/`bootJar`;
если `dist` нет (чистый бэкенд-прогон), jar соберётся без встроенного UI. В Docker
статику собирает отдельная node-стадия — вручную запускать npm не нужно.

## Профили конфигурации

`application.yml` содержит только общие настройки; окружение выбирает профиль.

| | `local` (по умолчанию) | `prod` |
|---|---|---|
| БД | `localhost:5432`, пароль с дефолтом | всё из env, дефолтов нет |
| Дашборд | `admin` / `changeit` | `DASHBOARD_USER` / `DASHBOARD_PASS` |
| Ключ шифрования секретов | дефолт `local-dev-key` | `SETTINGS_SECRET_KEY`, обязателен |
| Rate limit | 600 запросов/мин | боевые лимиты |
| Cookie `Secure` | выключен (http) | включён (нужен HTTPS) |
| `X-Forwarded-*` | не доверяем | доверяем (только за реальным reverse proxy!) |
| Логи | `DEBUG` по приложению | `WARN` |

Сам `application-prod.yml` в репозиторий не коммитится — рядом лежит
`application-prod.yml.example`. После клонирования:

```bash
cp src/main/resources/application-prod.yml{.example,}
```

Без этого файла профиль `prod` просто не существует и приложение не поднимется.

В `prod` секреты заданы как `${VAR}` **без дефолтов** — если переменная не
задана, приложение не стартует. Это намеренно: молчаливый запуск с дев-ключом
шифрования означал бы, что все сохранённые пароли расшифровываются неверно.

Сменить профиль вручную:

```bash
SPRING_PROFILES_ACTIVE=prod ./gradlew bootRun
```

> `TRUST_FORWARDED_HEADERS` включайте только если перед сервисом действительно
> стоит nginx/traefik — иначе заголовок `X-Forwarded-For` можно подделать и обойти
> rate limit.

## Настройка почтового ящика (Gmail)

Для Gmail нужны стандартные хосты + **пароль приложения** (обычный пароль от
аккаунта не подойдёт — Google не принимает его для IMAP/SMTP).

Серверы Gmail:

| Протокол | Хост | Порт | Шифрование |
|----------|------|------|-----------|
| IMAP (приём)  | `imap.gmail.com` | `993` | SSL |
| SMTP (отправка) | `smtp.gmail.com` | `465` | SSL (рекомендуется) или `587` STARTTLS |

Шаги:

1. **Включите IMAP в Gmail:** веб-Gmail → ⚙️ «Все настройки» → вкладка
   «Пересылка и POP/IMAP» → включить IMAP → сохранить.
2. **Включите 2-этапную аутентификацию:** `myaccount.google.com` → «Безопасность»
   → «Двухэтапная аутентификация» (без неё пароли приложений недоступны).
3. **Создайте пароль приложения:** `myaccount.google.com/apppasswords` → задайте имя
   (например `signet`) → Google выдаст **16-значный пароль** вида
   `abcd efgh ijkl mnop`. Скопируйте его **без пробелов**.
4. Заполните переменные (для первого ящика; см. `app.mailboxes` в `application.yml`):
   ```
   IMAP_HOST=imap.gmail.com
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=465
   SMTP_SSL=true
   SMTP_STARTTLS=false
   MAIL_USER=your_address@gmail.com
   MAIL_PASS=abcdefghijklmnop          # 16 символов пароля приложения, без пробелов
   AUTHOR_PROFILE=Иван, менеджер поддержки; пишу кратко и по делу
   ```

   `AUTHOR_PROFILE` — профиль автора (имя, факты о себе, тон общения). Подставляется
   в системный промпт вместо плейсхолдера `{profile}`, чтобы черновики шли от лица
   конкретного человека.

Нюансы:

- `MAIL_USER` — это и логин, и адрес отправителя (один аккаунт для чтения и отправки).
- Если нет пункта «Пароли приложений» — не включена 2FA (шаг 2) или это Workspace-аккаунт
  с запретом от админа (тогда пароль приложения включает администратор).
- Порт `587` со STARTTLS тоже работает (`SMTP_PORT=587`, `SMTP_SSL=false`, `SMTP_STARTTLS=true`),
  но при блокировках сети `465` обычно надёжнее.
- Некоторые провайдеры/сети режут исходящий SMTP — проверить можно так:
  `openssl s_client -connect smtp.gmail.com:465 -crlf` (должно прийти `220 ... ready`).
  Для локального теста без реальной отправки удобно поднять Mailpit (см. ниже).

### Несколько ящиков

`application.yml` → `app.mailboxes` — список. Первый заполняется из env выше,
остальные добавляются блоками; у каждого свои IMAP/SMTP и `profile` (профиль автора).
Ответ уходит через тот ящик, на который пришло письмо. Валидирует один менеджер
(в сообщении Telegram указан ящик).

### Синхронизация почты

Фонового опроса IMAP по расписанию **нет** — обращения к почте происходят только:
- **один раз при старте** приложения (первичное наполнение зеркала);
- **автоматически при открытии папки** в разделе «Почта» — быстрый точечный синк
  только этой папки (`POST /api/mail/{ящик}/sync?folder=…`), не чаще раза в минуту;
  список при этом показывается из зеркала мгновенно, обновление идёт фоном;
- **по кнопке «🔄 Синхронизировать»** — полный обход всех папок ящика
  (`POST /api/mail/{ящик}/sync`);
- точечно при открытии письма (ленивая дозагрузка тела) и действиях ответа.

Так число IMAP-подключений минимально (нет риска блокировки со стороны провайдера),
а свежесть почты контролируете вы. Синк за одно соединение обновляет папки, новые
письма и флаги; тела нескольких самых свежих писем INBOX подгружаются сразу,
остальные — лениво при первом открытии.

### Локальный тест отправки (Mailpit)

Чтобы проверить весь путь без реальной почты:

```bash
docker run -d --name mailpit -p 1025:1025 -p 8025:8025 axllent/mailpit
```
Переменные: `SMTP_HOST=localhost`, `SMTP_PORT=1025`, `SMTP_AUTH=false`,
`SMTP_STARTTLS=false`, `SMTP_SSL=false`. Отправленные ответы — на http://localhost:8025.

## Telegram-бот

Черновики на валидацию уходят менеджеру в Telegram. Бот работает по **long polling**
— публичный webhook и белый IP не нужны.

### 1. Создать бота и получить токен

1. Открой в Telegram **[@BotFather](https://t.me/BotFather)**.
2. Отправь `/newbot`, задай имя и username (должен заканчиваться на `bot`).
3. BotFather пришлёт **токен** вида `123456789:AAExampleToken...` — это `TG_BOT_TOKEN`.
   (Токен можно перевыпустить командой `/token`.)

### 2. Узнать chat_id менеджера

1. **Напиши своему боту** любое сообщение (например `/start`) — бот не может написать
   первым, пока ты ему не написал.
2. Узнай свой `chat_id` одним из способов:
   - через **[@userinfobot](https://t.me/userinfobot)** — пришлёт твой `Id` (число), или
   - открой в браузере `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найди
     `"chat":{"id":123456789,...}`.
3. Это число → `TG_MANAGER_CHAT_ID`.

### 3. Прописать переменные

```
TG_BOT_TOKEN=123456789:AAExampleToken...
TG_MANAGER_CHAT_ID=123456789
```

Нюансы:

- Для личного чата `chat_id` — положительное число. Для **группы** добавь бота в
  группу, напиши там сообщение — в `getUpdates` id будет отрицательным
  (`-100...`), его и укажи.
- Если Telegram не настроен, в логе будет `Telegram не настроен — бот не запущен`,
  и валидация работать не будет.

### Что видит менеджер

Под каждым письмом: ящик, отправитель, оригинал письма + перевод на русский,
черновик ответа + перевод, **вложения письма отдельными файлами**, и кнопки:
- **✅ Одобрить** — отправить как есть;
- **✏️ Редактировать** — прислать исправленный текст (на русском) ответным
  сообщением; сервис переведёт его на язык клиента и отправит;
- **❌ Отклонить** — ничего не отправлять.

## Доставляемость

Отправка идёт через SMTP существующего ящика поддержки (модель почтового клиента),
поэтому SPF/DKIM/репутацией занимается почтовый провайдер. Единственное
ограничение — суточный лимит отправки провайдера.
